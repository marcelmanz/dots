# Branch explained

Produce a single-use, local, interactive website that teaches what the current
branch implements, why each part is shaped the way it is, and how it got there
commit by commit. The reader is the user: they want to understand the code
properly, not skim a summary. Clean code is not a goal; correctness and clarity
are.

The test the page must pass: someone who has never opened this code reads it
once, plays with the widgets, and can then follow the real files and defend
every decision in review.

## Output

- Location: a new folder in the home directory, `~/<topic>-explained/`, where
  `<topic>` is a short kebab name for what the branch builds (e.g.
  `resources-api-explained`). Never inside the repo. Ask only if the user named
  another place.
- Files:
  - `index.html` from `assets/template.html`
  - `style.css` copied from `assets/style.css`
  - `engine.js` copied from `assets/engine.js`
  - `gen_data.py` copied from `assets/gen_data.py`
  - `data.js` generated by it
  - `content.js` with `window.PAGE`, written by you
  - `widgets.js` with the bespoke widgets for this branch, written by you
- Plain static files, opened with `file://`. No build, no server, no external
  network: no CDNs, no web fonts. Everything inline or local.
- Do not commit anything anywhere. Do not touch the repo's working tree.

## Process

### 1. Pin down the branch

- `git log --oneline` and `git branch -a` in the repo. Find the commit where
  the branch's own work starts. Do not assume `main`: the branch may have been
  cut from `development` or another feature branch, and `main` may be stale.
  Pick the base that gives the smallest set of commits that are all this
  branch's work, usually the last merge commit before the first own commit or
  `git merge-base HEAD <parent>`. If two bases are plausible, ask.
- `git diff --stat <base>..HEAD` for the touched files.
- Note uncommitted planning docs in the tree (PLAN.md, TODO.md, notes). They
  explain intent, but check them against the code: they go stale.

### 2. Generate the data

```
mkdir -p ~/<topic>-explained && cd ~/<topic>-explained
cp <skill>/assets/{style.css,engine.js,gen_data.py} .
python3 gen_data.py --repo <repo> --base <base> --head <branch> --out data.js <main files...>
```

Pass the 2 to 5 files that hold the real logic, plus its main test file, in
reading order. Skip build files, lockfiles and docs; their changes still show
up in the commit story.

### 3. Read everything, then decide

Read, in this order, before writing any page content:

1. Every commit diff, oldest first (`git log --reverse -p <base>..HEAD`). For
   each commit note what changed, why (from the message, the diff and what came
   before and after), and anything it broke or left behind that a later commit
   fixed.
2. The final versions of the changed files, in full.
3. The code around them: callers, wiring and registration, the patterns copied
   from elsewhere in the repo, test doubles and mocks, the build config, and
   the API docs or contracts the code must match.
4. Library sources when a behaviour depends on them (type mappings, threading
   guarantees, error handling). Cite the exact file and line.

For a large branch (more than ~40 commits or ~2000 changed lines), fan the
commit reading out to subagents by phase and have each return per-commit
what/why/watch notes. Keep the final writing in the main context.

Then decide:

- Phases: 3 to 8 groups of consecutive commits that tell the story (e.g.
  scaffold, first implementation, tests and wiring, review fixes, redesign,
  polish). Every commit belongs to exactly one.
- Mechanisms: the 2 to 6 ideas that make the implementation work (a
  background sampler, a type mapping, a retry policy, a cache invalidation
  rule, a protocol handshake). Each becomes a topic section.
- Concepts: every piece of background knowledge the reader needs to
  understand those mechanisms (section 0, below).

### 4. Write the page

Copy `assets/template.html` to `index.html` and fill it in. Keep the section
ids and widget containers the engine uses (`#fileTabs`, `#codeView`,
`#phaseFilter`, `#phaseBar`, `#commitList`, `.player[data-scenarios]`,
`svg.arch[data-info]`, `.check input[data-k]`, `.chash[data-c]`). The nav is
built from the section headings.

Sections, in this order:

0. **Technical base** (`#base`). The first thing on the page. One `.concept`
   block per concept, numbered `01`, `02`... with a chip link to each at the
   top. Order them foundation first: a concept only uses concepts above it.
   Cover every concept the code relies on that a competent developer in another
   stack might not know: language features, concurrency primitives, OS
   interfaces, protocols, library mechanics, build and link behaviour, the test
   framework. Too many beats too few. Each concept answers:
   - what it is, from scratch, in plain words;
   - why this code needs it (the problem it solves here, with the failure you
     get without it);
   - how this code uses it, with a short real excerpt;
   - the trap, if any;
   - the commit that introduced or fixed it, as a `.chash` link.

   Each concept gets a visual, in this order of preference:
   - a step-through player (`PAGE.scenarios`) for anything about ordering or
     interleaving: races, locks, wakeups, async callbacks, retries, event
     loops, transactions, lifecycle and teardown. Show the broken
     interleaving first, then the fixed one, with the shared state changing
     at each step and `bad` or `good` on the final step;
   - an interactive widget in `widgets.js` for anything with inputs and an
     output: formulas, parsers, type mappings, unit conversions, sizes and
     limits, state machines, timing (sliders, inputs, presets, toggles);
   - an inline SVG diagram (`class="dia"`) for structure: process and thread
     layout, object trees, ownership, pipelines, layers;
   - a table for enumerable facts.

1. **What it is** (`#overview`). Lead paragraph; the contract (the public
   surface added or changed: endpoints, properties, functions, CLI flags,
   events) as a table with types and meaning; "The short version" as 3 cards;
   files touched with their role.
2. **How it flows** (`#arch`). One clickable SVG of the runtime path, from
   where a request or event enters to where it has its effect, including
   background work. `PAGE.arch` holds each box's explanation.
3. **One section per mechanism.** Explain it, show the code, give a table of
   "tool, problem it solves, commit". Each one gets an interactive widget fed
   by realistic values: a calculator, a playground that maps choices to
   outcomes, or a simulator with toggles that switch off individual fixes so
   the reader sees what each commit protects against. Compare the before and
   after behaviour when the branch changed its mind.
4. **Code explorer** (`#code`). Driven by `PAGE.codeNotes`: for each file,
   ranges `{ from, to, c, t }` covering every non-trivial block. `t` explains
   what the block does and why, `c` is the commit that shaped it. Line numbers
   must match the final file exactly; verify them with `grep -n`.
5. **Commit story** (`#story`). Driven by `PAGE.notes`: one entry per commit,
   `{ p, what, why, watch? }`. `what` is concrete (names, values, files).
   `why` gives the reason, including the review feedback or bug that prompted
   it. `watch` flags what the commit got wrong or left for later, and which
   commit fixed it (e.g. an intermediate commit that doesn't compile).
6. **Decisions** (`#decisions`). Decision, alternative, why this one.
   Include the alternatives the branch tried and dropped.
7. **Tests** (`#tests`). How the test harness works, what each test proves,
   and what the tests cannot catch, stated plainly.
8. **Loose ends** (`#loose`). A checklist of things noticed while reading:
   stale docs or comments, TODOs, mismatches between code and docs or plans,
   edge cases, open verification steps. Each with `file:line`. Only real
   findings, each one verified.
9. **Try it** (`#tryit`). Exact commands to build, test and observe it live,
   with the flags whose absence makes it look broken, plus the `gen_data.py`
   command to refresh the data.

Number the headings in order (0, 1, 2, ...). Add topic sections between
`#arch` and `#code`. The engine needs no change for that.

### 5. `content.js`

```js
window.PAGE = {
  lang: "cpp",                         // highlighter: cpp c ts js python go rust java kotlin csharp shell nix
  phases: { 1: { name: "Scaffold", desc: "..." }, 2: { ... } },
  notes: { "abc1234": { p: 1, what: "...", why: "...", watch: "..." } },
  codeNotes: { "src/foo.cpp": [{ from: 10, to: 24, c: "abc1234", t: "<b>Name.</b> ..." }] },
  scenarios: {
    lostUpdate: {
      title: "Lost update",
      init: { count: 5 },
      threads: [{ name: "Thread A", code: ["tmp = count;", "count = tmp + 1;"] }, { name: "Thread B", code: ["..."] }],
      steps: [{ t: 0, l: 0, s: { "A.tmp": 5 }, say: "..." }, { t: 1, l: 1, s: { count: 6 }, bad: true, say: "..." }],
    },
  },
  arch: { boxKey: "<b>Title</b><p>...</p>" },
};
```

Strings are HTML. Use `<code>` for identifiers and
`<span class="chash" data-c="abc1234">abc1234</span>` for commit links; the
engine makes them jump to the commit. Hash length must match `data.js`.

### 6. `widgets.js`

Bespoke widgets for this branch, as plain DOM code with no framework. Use the
helpers the engine exposes: `esc`, `bindHashes`, `commitByHash`, `PHASES`.
Use the CSS tokens (`var(--accent)`, `--p1`..`--p8`, `--add`, `--del`,
`--warn`, `--code-bg`) so light and dark mode both work. Animated simulators
run on simulated time, scaled to a few real seconds per cycle. Each widget
needs a clear initial state and a reset.

## Verify

1. `node --check engine.js content.js widgets.js`.
2. Screenshot every section with headless Chromium and look at each image:
   - add a temporary `_test.html` that hides all other sections
     (`main>section:not(#x){display:none}`) and clicks a few buttons on load;
   - render with a tall window (`--window-size=1400,1500
     --virtual-time-budget=4000`);
   - scrolling inside headless pages renders blank, so hide sections instead
     of scrolling;
   - snap Chromium cannot write to `/tmp`, so write the screenshot inside the
     output folder.
   Fix overlapping SVG text, arrows crossing boxes, clipped labels, wrapped
   code lines and empty widgets.
3. Click a code line in the test page (last action, nothing clicked after it,
   since any outside click closes the tooltip) and check with `--dump-dom` that
   `#codeTip` is not hidden and shows the right range and commit.
4. Check every commit has a note, every `codeNotes` range matches the file,
   and every hash in the HTML exists in `data.js`.
5. Delete `_test.html` and screenshots with `rm -f` (`rm` may be aliased to
   ask for confirmation, which hangs a non-interactive shell).

## Writing rules

- Every claim comes from the code, the diffs or a cited source. When unsure,
  check; if it can't be checked, say so in the text.
- Explain why, not only what. A decision without its reason is not understood.
- Name the traps: the ordering that matters, the flag whose absence breaks it,
  the asymmetric contract.
- Short sentences, plain words, no marketing tone, no emojis.
- Tables for enumerable facts, prose for cause and effect, widgets for
  behaviour.
- Never put secrets, tokens or credentials from the repo into the page.

## Report back

Tell the user the folder and the `file://` URL, list the sections and the
interactive parts, say what was verified and how, and list the loose ends
found.
